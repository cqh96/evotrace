## 1. 背景与问题

### 1.1 业务背景

软件系统在日常开发中不断迭代：需求变更、功能新增、逻辑重构、缺陷修复、依赖升级……代码持续被修改，但"系统逻辑在某一刻到底是什么样子"却越来越难回答。更关键的是，**产品经理、开发工程师、测试工程师、运维工程师四者之间的信息断层**：

- **PM 视角**：我写的需求开发到哪了？关联了哪些代码？什么时候能上线？
- **Dev 视角**：这段代码是哪个需求驱动的？改了之后会影响谁？
- **QA 视角**：这次发版改了哪些文件？该回归哪些测试用例？发现的 Bug 是谁的提交引入的？
- **Ops 视角**：这个版本能不能发？质量门禁过了没有？上线后出了故障怎么快速定位变更引入点？

EvoTrace 的答案是：**用一个平台打通「需求 → 代码 → 测试 → 缺陷 → 发布」全链路**，让 PM、Dev、QA、Ops 各自看到自己关心的视图，同时所有信息在底层互联互通。

### 1.2 产品定位

EvoTrace 是一个**覆盖软件全生命周期的演化追踪与智能分析平台**：

- **记录链路**：业务迭代 ↔ 代码修改 ↔ 测试验证 ↔ 缺陷修复 ↔ 版本发布
- **AI 语义化**：把 diff / 接口变更 / DDL 变更转译为业务可读描述
- **全角色赋能**：PM 需求看板、QA 测试推荐、Dev 变更追踪、Ops 质量门禁
- **任意技术栈接入**：Java（Starter）、Go/Python/Vue/Node（CLI）、Git Webhook

## 2. 核心概念模型

| 概念 | 定义 | 关键属性 |
| --- | --- | --- |
| 工作空间 Workspace | 多租户隔离单元 | 名称、成员、配额 |
| 项目 Project | 被追踪的系统/仓库 | 语言栈、仓库地址、接入方式 |
| 应用 Application | 可独立部署的单元 | 技术栈、负责人 |
| 业务需求 Requirement | PM 创建的业务诉求 | 标题、优先级、状态、原型链接、目标版本 |
| 业务迭代 Iteration | 外部需求系统的同步单元 | 标题、来源、状态 |
| 变更事件 ChangeEvent | 一次被采集的变更事实 | 类型、时间、作者、diff |
| 版本 Release | 语义化发布点 | 版本号、基线 commit、发布时间 |
| 快照 Snapshot | 某时间点系统逻辑的结构化描述 | 类型、内容哈希 |
| 测试用例 TestCase | QA 编写的测试场景 | 关联需求、关联文件、测试步骤 |
| 测试执行 TestExecution | 用例执行记录 | 状态、执行人、执行时间 |
| 缺陷 BugTicket | QA 发现的软件缺陷 | 严重级别、状态、发现版本、修复版本 |
| 质量门禁 QualityGate | 发布前的准入检查 | 检查项结果、通过/失败 |
| AI 语义单元 SemanticUnit | AI 生成的自然语言产物 | 类型、模型、置信度 |
| 演化链 EvolutionChain | 从需求到发布的有向链路 | 双向可遍历 |

## 3. 功能需求

### 3.1 FR-1 项目接入管理（已实现）

- FR-1.1 创建项目与应用，生成项目级 API Key（轮换/吊销/按环境区分）
- FR-1.2 四种接入方式：Java SDK / CLI 扫描器 / Git Webhook / Open REST API
- FR-1.3 接入向导 + 验证回执 + 接入健康看板

### 3.2 FR-2 变更采集（已实现）

- FR-2.1 代码变更：commit/MR 级 diff 采集
- FR-2.2 接口变更：REST/RPC 接口清单的版本间 diff
- FR-2.3 依赖变更：构建文件版本间 diff
- FR-2.4 配置变更：配置快照差异（敏感值脱敏）
- FR-2.5 数据库结构变更：DDL diff（表/字段/索引级）
- FR-2.6 幂等与顺序：事件 ID 幂等、同分支 commit 拓扑序归并
- FR-2.7 变更与需求关联：commit message 正则提取需求号

### 3.3 FR-3 版本与快照（已实现）

- FR-3.1 版本登记：git tag / 发版单 API
- FR-3.2 快照生成：接口/依赖/配置/DDL/模块结构
- FR-3.3 增量快照 + 周期强基线
- FR-3.4 内容寻址存储：按哈希去重
- FR-3.5 快照回放：任意版本系统逻辑全貌

### 3.4 FR-4 演化链路与对比（已实现）

- FR-4.1 演化时间线：按应用/作者/类型过滤
- FR-4.2 版本对比：接口/依赖/配置/DDL/代码统计五维度
- FR-4.3 双向追溯：需求→变更→版本 / 版本→变更→需求
- FR-4.4 文件级历史：单文件演化历史视图

### 3.5 FR-5 AI 智能能力（已实现）

| 编号 | 功能 | 状态 |
| --- | --- | --- |
| FR-5.1 | 变更智能摘要：diff → 业务语义描述 | ✅ 已实现 |
| FR-5.2 | 版本发布说明生成：按模块生成 Release Notes | ✅ 已实现 |
| FR-5.3 | 影响面分析：基于依赖图推断影响的应用与接口 | ✅ 已实现 |
| FR-5.4 | 演化问答（RAG）：自然语言查询演化历史 | ✅ 已实现（关键字检索 + M3 RAG升级） |
| FR-5.5 | 破坏性变更检测：识别不兼容变更并告警 | ✅ 已实现 |
| FR-5.6 | 代码热点分析：高频变更文件/缺陷倾向文件/共变耦合 | ✅ 已实现 |

### 3.6 FR-6 发布风险管理（V2.0 新增，已实现）

| 编号 | 功能 | 说明 |
| --- | --- | --- |
| FR-6.1 | 发布风险评分 | 综合变更量(30%)、破坏性变更(25%)、历史缺陷(20%)、影响半径(15%)、时间因子(10%)，输出 0-100 分 |
| FR-6.2 | 风险趋势 | 版本间风险评分历史曲线 |
| FR-6.3 | 破坏性变更告警 | 接口删除/字段收窄/DDL删列/依赖大版本升级，分级（CRITICAL/WARNING/INFO）推送 |

### 3.7 FR-7 质量门禁（V2.0 新增，已实现）

| 编号 | 检查项 | 权重 |
| --- | --- | --- |
| FR-7.1 | 未关闭 P0/P1 缺陷数 | 30 分 |
| FR-7.2 | 测试用例通过率 | 25 分 |
| FR-7.3 | 未确认破坏性变更 | 20 分 |
| FR-7.4 | 变更文件测试覆盖率 | 15 分 |
| FR-7.5 | 发布风险评分 | 10 分 |

### 3.8 FR-8 PM 赋能（V2.0 新增，已实现）

- FR-8.1 需求看板（Kanban）：按状态分列，拖拽流转（DRAFT → REVIEW → DEVELOPING → TESTING → DONE）
- FR-8.2 需求关联统计：每张卡片显示关联的代码提交数 / 测试用例数 / 未关闭缺陷数
- FR-8.3 原型/设计稿链接：支持 Figma、蓝湖、Axure 等 URL
- FR-8.4 需求→代码双向追溯：点击需求看所有关联变更；点击变更看所属需求
- FR-8.5 变更通知：需求状态变更时自动通知 QA

### 3.9 FR-9 QA 赋能（V2.0 新增，已实现）

- FR-9.1 变更驱动的测试推荐引擎：输入 fromVersion → toVersion，自动匹配关联的测试用例
- FR-9.2 回归范围生成：按影响半径给出建议回归范围（P0 优先 / P1 / 回归用例）
- FR-9.3 Bug → Commit 追溯：每个 Bug 可追溯到修复提交、引入提交、受影响文件、关联测试用例
- FR-9.4 Bug 自动关联：创建 Bug 时自动匹配关联需求下的相关变更
- FR-9.5 发布准入检查：QA 一键检查目标版本是否满足发布条件

### 3.10 FR-10 智能订阅与通知（V2.0 新增，已实现）

- FR-10.1 变更订阅：按项目 / 事件类型 / 文件 glob 模式 / 应用设置订阅规则
- FR-10.2 多渠道推送：飞书 / 钉钉 / 企业微信 / 自定义 Webhook
- FR-10.3 PM/QA 定向通知：需求进入测试/接口破坏性变更/测试失败时定向推送
- FR-10.4 通知日志：可追溯所有通知历史

### 3.11 FR-11 端到端全链路追踪（V2.0 新增，已实现）

- FR-11.1 从任意节点追溯全链路：需求→迭代→代码→测试用例→缺陷→版本
- FR-11.2 版本发布全景视图：一个页面看版本关联的所有需求/变更/缺陷/测试
- FR-11.3 可视化链路图：物化 E2E trace 路径

### 3.12 FR-12 多 Git 平台 Webhook（已实现）

- FR-12.1 GitLab Webhook：push / merge_request / tag_push
- FR-12.2 GitHub Webhook：push / pull_request / create(tag) / ping
- FR-12.3 统一 Envelope 转换，无缝对接采集管道

## 5. 非功能需求

| 类别 | 要求 |
| --- | --- |
| 性能 | 变更事件摄入 ≥ 500 events/s；版本对比 P95 < 5s；AI 摘要异步生成 |
| 可用性 | 核心摄入链路 99.9%；AI 服务降级自动跳过、事后补跑 |
| 存储 | diff 原文压缩存储；快照增量去重；按项目配置保留策略 |
| 安全 | 多租户隔离；RBAC；API Key + HMAC 签名鉴权；敏感值强制脱敏；审计日志 |
| 隐私 | 支持全私有化部署；云端模型调用可逐项目关闭或降级 |
| 扩展性 | 接入解析器插件化；AI 模型提供方插件化；事件协议版本化 |

## 7. 验收标准（V2.0）

1. PM 创建需求 → 关联原型链接 → 流转到 TESTING → QA 收到通知
2. QA 在测试面板输入 fromVersion/toVersion → 获得推荐测试用例列表 + 回归范围
3. QA 提交 Bug → 自动关联该需求下的最近变更 → 可追溯修复提交
4. PM 执行质量门禁 → 5 项检查全部执行 → 有 P0 Bug 时门禁 FAILED（得分 70/100）
5. DevOps 查看 E2E Trace /release/v2.5.0 → 看到该版本的全部需求/变更/缺陷/测试摘要
6. 开发者在 Cursor 中右键文件 → 查看演化历史 → 展示该文件所有变更 + AI 摘要
7. 配置订阅规则 "DDL_CHANGE + **/payment/**" → 匹配时推送飞书通知
8. GitHub push 事件 10 秒内出现在时间线
