## 1. 总体结论

两份文档结构完整、工程化程度高，Phase A 规格细化到表结构 / API / 前端字段级，可直接作为联调契约与任务拆分依据。但经与现有代码库交叉核对，发现**若干与现状 schema 冲突或内部自相矛盾的问题**，其中 3 项属 P0 级，会直接导致 Phase A 部分功能无法按文档实现，建议在编码前先修订方案，避免返工。

---

## 2. 文档优点

1. **架构分层清晰**：§2 链路内核先定义工件类型 / 边类型 / 统一 Trace API，再在 §3–§5 展开增强项与分期，符合"先内核后功能"原则。
2. **务实边界**：§0.4 明确"不补"清单（工时 / 甘特 / Wiki 等），§8.1 界定 Phase A 范围与非范围，避免范围膨胀。
3. **兼容策略到位**：§8.2.7 双写规则保留旧字段、§8.10 风险对策、特性开关 `evotrace.trace.v2.enabled`，向后兼容设计成熟。
4. **§8.7 验收剧本 A1–A9** 每一步有明确"步骤 → 期望"，可测试、可验收。
5. **Issue 清单** 依赖关系清晰、预估合理、给出并行波次；A-DB-1 已落地（`V18__trace_core.sql` 与文档 §8.2 基本一致）。
6. **完整度权重与门禁算法**权重合计 = 100，边界条件（`GATE_PASS_IF_RELEASED`）定义合理。

## 3. 存在的问题与改进建议（按优先级）

### 3.1 P0 —— 会阻塞 Phase A 实现，必须先修订

#### P0-1｜commit message 未入库，导致治理 / 悬空键 API 无法落地

**现状事实**

- `change_event` 表没有任何 message / commit_message 列（见 `V1__init.sql` §`change_event`）。
- `CommitHandler` 只在摄入时从 `payload.message()` 解析 `iteration`，消息文本**未持久化**。

**文档冲突点**

- §8.4.3 `unlinked-changes` 响应含 `message` 字段。
- §8.4.3 `dangling-keys` 响应含 `message`。
- §8.6.1 悬空键检测："治理查询时规则抽取 commit message 的 key"——查询时消息已不在库中，无法抽取。

**建议与理由**

新增 `change_event.message VARCHAR(1024)`（`change_event` 为 RANGE 分区表，`ALTER TABLE` 会自动透传到各分区）。这样 governance 查询、悬空键即时检测才有数据来源。`LinkRuleEngine` 在摄入期用内存 `message` 建边可行，但 `matchedText` 应写入 `artifact_link.meta`（文档已如此约定），否则待确认列表同样取不到命中文本。

#### P0-2｜默认 REQ 规则正则与自动生成键互相矛盾，小 id 需求无法自动关联

**现状事实**

- 自动生成键为 `REQ-{id}`（V18 回填 `'REQ-' || id`）。
- 默认规则正则要求 `REQ[-_]?\d{3,}`，即键至少 3 位数字。

**问题**

当 `requirement.id < 100` 时，生成键为 `REQ-5`、`REQ-42`，**不匹配** `\d{3,}`，这些需求的 commit 无法通过 REQ 规则自动挂边（可能被 JIRA 规则以错误语义命中）。

**建议与理由**

二选一并固化：(a) 生成键规范化补零为 `REQ-0005`（需同步改回填 SQL 与创建逻辑）；(b) 放宽规则为正则 `REQ[-_]?\d+`。推荐 (a)，保证键位一致、可读、排序友好。文档 §8.2.2 默认种子规则与 `ReqKeyService` 规格需同步更新。

#### P0-3｜`/trace/overview/release/{version}` 无应用维度，存在跨 app 版本歧义

**现状事实**

- `release` 表 `app_id NOT NULL`，且 `UNIQUE (project_id, app_id, version)`。同一项目内不同应用可存在相同 `version`。

**文档冲突点**

- §8.4.5 用 `version` 作唯一路径参数。
- §8.4.5 ChangeSet 纳入规则未含 app 维度。

**建议与理由**

release overview / rebuild 应改为按 `release id`（或 `version + appId`）定位，ChangeSet 时间窗规则明确限定 `app_id`。否则多应用项目下返回 / 重建结果不确定。

### 3.2 P1 —— 正确性 / 一致性，建议在 Phase A 内修正

#### P1-1｜文档与 V18 实现不一致

**问题**

- 文档 §8.2.4 定义索引 `idx_artifact_link_pending ON (project_id, status, confidence) WHERE status IN ('PENDING','ACTIVE')`，但 V18 实际为 `idx_artifact_link_status ON (project_id, status, confidence)`（无过滤条件）。
- 文档 §8.2.4 `source` 枚举未列 `AUTO_TIME_WINDOW`，但 V18 注释已含，且 §8.4.5 的 ChangeSet 规则使用该 source。

**建议与理由**

以"文档为准"或"以已落库为准"二选一，统一起来，避免后续 A-BE-2 / A-BE-5 实现时按错误索引预期优化。

#### P1-2｜`req_key` 前缀变更后新旧键格式不一致

**问题**

§8.4.2 生成方案为 `{prefix}-{id}`，若项目将 prefix 从 `REQ` 改为 `PAY`，历史键仍为 `REQ-{id}`，新键为 `PAY-{id}`，同一项目内键语义 / 排序混乱，且默认 REQ 规则与新前缀不匹配。

**建议与理由**

明确"前缀变更策略"——不支持运行中变更；或变更时提供一键迁移回填；`project_link_rule` 与 `project_trace_setting.req_key_prefix` 需联动。

#### P1-3｜`hash_issue_enabled` 的映射语义含糊

**问题**

§8.2.3 注释 `#123 → 需求 id/external`，但 `requirement.id` 是全局自增（非项目内序号），`external_key` 又非项目内唯一约束，映射目标不明确。

**建议与理由**

明确 `#N` 映射到"项目内 `req_key` 数字段"还是"全局 id"，并补唯一性校验；否则悬空键 / 误关联风险高。

#### P1-4｜`trace/rebuild` 与治理查询缺少时间窗兜底

**问题**

`change_event` 为 `RANGE(occurred_at)` 分区表。治理 `unlinked-changes` 的 `from/to` 为可选参数，缺省时全分区扫描代价高。

**建议与理由**

治理查询强制 / 默认带时间窗（如近 90 天），保证分区裁剪生效，并在 API 文档注明。
