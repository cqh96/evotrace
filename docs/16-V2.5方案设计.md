## 1. 背景与目标

### 1.1 背景

V2.1（M-Trace-A）已打通"需求 → 代码 → 测试 → 缺陷 → 发布"全链路，并落地了 Trace Core 治理能力。V2.5 的目标是**从"单机私有化工具"演进为"生产级可交付、可规模化、可扩展的平台"**，核心诉求：

1. **交付**：从 docker-compose 单机扩展到 Kubernetes/Helm 生产级编排。
2. **规模化**：事件/分析大数据从 PostgreSQL 分流到 ClickHouse 列式分析，支撑高并发写入与秒级聚合。
3. **可扩展**：解析器（代码/接口/DDL/配置解析）插件化 + 插件市场，生态共建。
4. **深度对接**：GitLab 仓库从"被动收 Webhook"升级为"主动仓库级分析"。
5. **可信**：性能压测体系，量化摄入/查询吞吐与延迟，支撑 SLA 与容量规划。

### 1.2 目标

| 维度 | 目标 |
| --- | --- |
| 部署 | 提供 Helm Chart，支持多副本、滚动升级、HPA、可观测采集 |
| 分析 | 事件/分析类查询走 ClickHouse，PostgreSQL 只保留业务事务数据 |
| 生态 | 解析器 SPI + 插件市场（仓库/校验/安装/版本管理） |
| GitLab | 支持导入 GitLab 自建仓库，主动 clone + 增量分析 + MR/Commit 全量喂入 |
| 压测 | 提供基准测试脚本 + 报告模板，量化关键路径 SLA |

## 2. 现状与差距分析

| 能力 | 现状（V2.1） | V2.5 差距 |
| --- | --- | --- |
| 部署 | `docker-compose.yml` 单机 | 需 Helm Chart + 可观测 + 多副本 |
| 存储 | RDS PostgreSQL 承载全部（含事件/分析） | ClickHouse 接手事件流与分析查询 |
| 解析 | `snapshot` 内容寻址 + Analysis 引擎硬编码多种解析器 | 解析器 SPI 化 + 市场分发 |
| GitLab | 仅 Webhook（push/MR/tag）单向接收 | 主动仓库导入、clone、增量分析、回写 |
| 性能 | 无系统化基准 | 基准场景 + 报告 + 阈值基线 |

> 说明：多租户（workspace 成员/配额/套餐）不在 V2.5 范围，插件安装与既有数据保持全局/按项目维度，避免引入租户隔离改造。

## 3. 五项范围设计

### 3.1 Helm Chart 部署

#### 3.1.1 目标

将 docker-compose 单机编排升级为可生产交付的 Kubernetes 编排，支持多副本、滚动升级、HPA、可观测采集。

#### 3.1.2 组件清单

| 组件 | 说明 | 备注 |
| --- | --- | --- |
| evotrace-server | 平台服务端（无状态，可 HPA） | Stateless，Pod 间无共享状态 |
| evotrace-ui | 前端静态资源 | 由 Nginx/Ingress 托管 |
| PostgreSQL + pgvector | 业务事务库 | StatefulSet / 外部托管 |
| Redis | 缓存/会话 | 可选，外部托管 |
| Kafka | 事件队列 | Strimzi / 外部托管 |
| MinIO | 对象存储（blob/diff） | 可选，外部 S3 |
| ClickHouse | 分析库（见 3.2） | 外部托管 |
| evotrace-worker | AI 消费者（可独立扩缩） | 与 server 解耦，便于异步扩缩 |

#### 3.1.3 Chart 结构

```
charts/evotrace/
├── Chart.yaml
├── values.yaml            # 集中配置：镜像、副本、资源、存储、外部依赖地址
├── values-{{env}}.yaml    # 环境覆盖（dev/staging/prod）
└── templates/
    ├── deployment-server.yaml / deployment-worker.yaml
    ├── hpa.yaml / pdb.yaml / priorityclass.yaml
    ├── service.yaml / ingress.yaml
    ├── configmap.yaml / secret.yaml
    ├── serviceaccount.yaml / rbac.yaml
    └── _helpers.tpl
```

#### 3.1.4 关键设计

- **配置外部化**：全部依赖（DB/Redis/Kafka/CH/MinIO）通过 ConnectionConfig 注入，不内嵌。
- **可观测**：sidecar 注入 OpenTelemetry Agent，指标/链路/JVM 采集到 Prometheus + Grafana。
- **健康检查**：`/actuator/health` 探针 + `startupProbe`（AI 预热）。
- **权限**：`automation_rule`/`subscription` 等定时任务在 worker 中运行，避免多副本重复执行（用 DB 分布式锁 / 分片）。

### 3.2 ClickHouse 分析库

#### 3.2.1 定位

PostgreSQL 保留**业务事务数据**（项目配置、需求、边、门禁、审计等）；ClickHouse 承接**高吞吐事件流 + 分析聚合查询**。

| 数据 | 落库 | 说明 |
| --- | --- | --- |
| change_event 原始事件 | ClickHouse（明细） | 列式，亿级无压力 |
| change_file 文件级 | ClickHouse | 按 event 关联 |
| 分析聚合（趋势/热点/风险时序） | ClickHouse 物化视图 | 秒级聚合 |
| 业务事务（项目/需求/边/门禁） | PostgreSQL | 保持事务一致性 |

#### 3.2.2 表设计（ClickHouse）

```sql
-- 事件明细（MergeTree 按 occurred 分区）
CREATE TABLE evo.change_event_local (
    id UInt64,
    project_id UInt64,
    app_id UInt64,
    event_id String,
    event_type LowCardinality(String),
    branch String,
    commit_sha String,
    author String,
    commit_message String,
    blob_ref String,
    occurred DateTime64(3)
) ENGINE = MergeTree
  PARTITION BY toYYYYMM(occurred)
  ORDER BY (project_id, occurred);

-- 分布式表（多副本/多分片）
CREATE TABLE evo.change_event AS evo.change_event_local ENGINE = Distributed(cluster, evo, change_event_local, rand());
```

- **物化视图**：`mv_daily_event_count`、`mv_hotspot_file`、`mv_risk_trend` 预聚合，业务侧直接查视图。
- **写入链路**：`IngestionService → Kafka evo.events.raw → ClickhouseEventSink`（批量 upsert，`ReplacingMergeTree` 或幂等 `INSERT` + 去重键）。
- **双写策略**：过渡期 PostgreSQL 与 ClickHouse 双写，`flag` 开关逐步灰度；稳定后 PostgreSQL 只保留近 N 天热数据用于事务回查，历史归档 CH。

#### 3.2.3 查询路由

- 事务 / 写操作 / 低频小数据 → PostgreSQL 数据源。
- 时间线列表 / 趋势 / 热点 / 风险时序 / 统计 → ClickHouse 数据源（`@ClickhouseRepository`）。

#### 3.2.4 迁移与回填

- 提供 `ClickhouseBackfillJob`：从 PostgreSQL 分区表分批导历史事件入 CH。
- 分区与保留策略对齐现有 `PartitionMaintainer`。

### 3.3 解析器插件市场

#### 3.3.1 目标

把"代码/接口/DDL/配置/依赖"解析从硬编码演进为**SPI 插件 + 市场分发**，支持第三方生态共建。

#### 3.3.2 解析器 SPI

```java
public interface ParserPlugin extends Plugin {
    /** 插件标识，如 vendor.parser.git-java */
    String id();
    /** 支持的类别：CODE / API / DDL / CONFIG / DEPENDENCY */
    Category category();
    int version();
    /** 输入物（blob/快照/仓库路径），输出归一化清单项 */
    ParseResult parse(ParseContext ctx);
}
```

统一由 `ParserRegistry` 按 `category + 版本` 路由到具体插件；快照/对比引擎不再关心具体解析实现。

#### 3.3.3 市场分发

- **形态**：可选两种，推荐先做 Jar 插件（贴合现有 Spring 生态）：
  1. **Jar 插件**：进入 `plugins/` 目录热加载（`URLClassLoader` + 隔离 ClassLoader），适配私有化。
  2. **独立服务插件**（高级）：gRPC/HTTP 协议，容器化部署，隔离更强。
- **市场目录**：`plugin_catalog`（云端索引）+ `plugin_release`（版本/校验和/兼容性）+ `plugin_install`（安装记录）。
- **安全**：插件签名校验（`SHA-256` + 签名）、沙箱（Jar 强制白名单包）、版本兼容声明、异常隔离。

#### 3.3.4 新增表（V20）

| 表 | 说明 |
| --- | --- |
| `plugin_catalog` | plugin_id、名称、分类、描述、作者、兼容版本 |
| `plugin_release` | plugin_id、version、jar_ref、sha256、signature、兼容基线 |
| `plugin_install` | `UNIQUE(plugin_id)`、enabled、installed_at |

> 无多租户，插件安装为全局/按项目维度，不引入 workspace_id。

#### 3.3.5 关键接口

```
/api/v1/plugins/catalog         GET         市场列表
/api/v1/plugins/{id}/releases   GET         版本列表
/api/v1/plugins/install         POST        安装
/api/v1/plugins/{id}/enable     PUT         启停
/api/v1/plugins/{id}/uninstall  DELETE      卸载
```

### 3.4 GitLab 仓库集成

#### 3.4.1 定位

从"被动收 Webhook"升级为"**主动仓库级集成**"：导入自建 GitLab 仓库，主动 clone + 增量分析，喂入既有事件管道，支撑离线/历史数据回填与更深的代码分析。

#### 3.4.2 能力

| 能力 | 说明 |
| --- | --- |
| 仓库导入 | 按 namespace/repo 导入，登记 `repo_url`、认证令牌 |
| 全量/增量 clone | JGit 克隆，事件采集器按 commit 拓扑序喂入 |
| MR/Commit 拉取 | GitLab REST/GraphQL 拉取历史 MR、Commit、Tag 批量回填 |
| 增量同步 | 定时/Webhook 触发增量拉取，回写状态 |
| 回写 | PR 描述生成、评审结果回写到 GitLab（新增/更新 MR note） |
| 凭证安全 | Personal/Group/Project Token 加密存储，按项目映射 |

#### 3.4.3 新增表（V21）

| 表 | 说明 |
| --- | --- |
| `gitlab_connection` | project、base_url、auth_type、token_enc、default_namespace |
| `repo_import` | project_id、repo_path、default_branch、clone_status、last_synced_sha、schedule |
| `repo_import_log` | 同步批次记录（状态、增量数、耗时） |

#### 3.4.4 关键接口

```
/api/v1/projects/{key}/gitlab/connect      POST   配置连接
/api/v1/projects/{key}/repos/import        POST   导入仓库
/api/v1/projects/{key}/repos/{id}/sync     POST   手动增量同步
/api/v1/projects/{key}/repos               GET    仓库列表与同步状态
```

#### 3.4.5 复用

仓库导入后直接复用现有 `IngestionService` + `CommitHandler`（同一事件管道），仅新增"仓库采集器"作为另一事件源。

### 3.5 性能压测

#### 3.5.1 目标

建立**可重复的基准测试体系**，量化关键路径并沉淀阈值基线，支撑 SLA 与容量规划。

#### 3.5.2 关键路径与指标

| 路径 | 指标 | 目标基线（单机参考） |
| --- | --- | --- |
| 事件摄入 | 吞吐 events/s、P95 端到端延迟 | ≥ 500 events/s；P95 < 2s |
| Webhook → 时间线可见 | 端到端延迟 | < 10s |
| 版本对比报告 | P95 延迟 | < 5s |
| 时间线查询 | P95 延迟 | < 1s（CH 加速后） |
| AI 摘要 | 吞吐、队列积压 | 异步，避免阻塞摄入 |

#### 3.5.3 方案

- **工具**：k6（协议/Webhook 压测）+ JMeter（可选）。压测脚本进仓库 `scripts/bench/`。
- **数据生成**：`scripts/bench/seed.py` 批量构造 Envelope 事件（可配置项目/文件/commit 规模）。
- **报告**：`scripts/bench/report.py` 汇总吞吐/延迟/错误率，输出 JSON + Markdown，与基线阈值比对（`thresholds.yaml`）。
- **CI 集成**：`deploy/` 增加 `bench-remote.sh`，发布前跑基准回归，超阈值即告警。

#### 3.5.4 基线仓库

| 配置 | 说明 |
| --- | --- |
| `thresholds.yaml` | 各路径 P95/吞吐阈值，按环境（dev/staging/prod）区分 |
| `profiles/` | 小/中/大（事件规模）三档压测 profile |

## 5. 风险与依赖

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 双写数据不一致 | 事件账目差异 | 幂等键 + ReplacingMergeTree 去重 + 对账 Job |
| 插件安全风险 | 恶意插件执行 | 校验和 + 签名 + 沙箱白名单 + 异常隔离 |
| GitLab Token 泄露 | 数据泄露 | token 加密存储、最小权限、审计 |
| ClickHouse 引入成本 | 运维复杂度上升 | 先托管版/外部依赖，避免自建集群运维 |
| 多副本 Worker 重复执行 | 定时任务重复 | DB 分布式锁 / 分片任务分配 |

## 6. 验收标准（V2.5）

1. 一个 Helm `helm upgrade --install` 即可拉起多副本 server + worker，滚动升级零中断。
2. 事件摄入后，时间线查询直接命中 ClickHouse，P95 < 1s（万级事件规模）。
3. 通过插件市场安装一个第三方解析器，无需改主代码即可识别新格式并产出快照。
4. 导入自建 GitLab 仓库后，历史 commit/MR 全量回填并出现在时间线，后续增量同步自动完成。
5. 运行 `scripts/bench/` 基准脚本，产出报告并判定是否达到阈值基线。
