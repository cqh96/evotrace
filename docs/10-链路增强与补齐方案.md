## 0. 背景与目标

### 0.1 问题

EvoTrace V2.0 已具备需求看板、变更采集、测试计划、缺陷、质量门禁、E2E API 等能力，但链路「不够清晰可追踪」，根因不是缺大模块，而是：

1. **关联不可靠**：commit 正则主要挂 `iteration`，与 `requirement` 非强边；测试推荐依赖 `ILIKE` 文本匹配。
2. **全景不成页**：`e2e_trace` 与分散 API 存在，但缺少统一「一张图 / 一页讲完」的产品主路径。
3. **治理动作缺失**：未关联提交、低置信度边、断链（有代码无用例等）无法日常运营。
4. **版本聚合口径不一**：Release 侧缺少明确 ChangeSet 与发布驾驶舱。

### 0.2 目标

| 编号 | 目标 |
| --- | --- |
| G1 | 任意节点（需求 / 提交 / MR / 用例 / 执行 / 缺陷 / 门禁 / 版本 / 部署）可双向走到全链 |
| G2 | 关联以结构化边为主，模糊匹配仅作降权兜底 |
| G3 | 状态流转、补链/断链、门禁豁免可审计 |
| G4 | PM/QA/Ops 在统一全景页回答「能不能发、缺什么、风险在哪」 |
| G5 | 各角色有主路径，不靠跨 10+ 页面拼故事 |

### 0.3 成功标准（可验收）

| 编号 | 标准 |
| --- | --- |
| S1 | 需求详情一页可见：任务、文档/原型、关联提交/MR、用例覆盖、执行、缺陷、目标版本、门禁 |
| S2 | 任意 commit/MR 一页可见：关联需求、影响文件/API、推荐/已执行用例、相关缺陷、所属 Release |
| S3 | 缺陷一页可见：引入提交、修复提交、失败用例、所属需求、发现/修复版本 |
| S4 | Release 一页可见：纳入需求、变更摘要、测试通过率、未关闭缺陷、门禁、部署 |
| S5 | 规范 commit 下，≥70% 的 `CODE_COMMIT` 自动挂到需求；人工补链可审计 |
| S6 | 追溯矩阵可按版本/迭代输出覆盖率与缺陷逃逸率，并支持下钻 |

### 0.4 设计原则

1. **放大差异化**：自动采集 + AI + 全链路追溯；不做成第二个 TAPD。
2. **先内核后功能**：统一 `artifact_link` + Trace API + 全景组件，再拧紧各角色体验。
3. **兼容双写**：旧字段（`requirement_id`、`bug_change_link`、`related_files` 等）可读；新写入双写边表。
4. **可开关**：`evotrace.trace.v2.enabled` 控制新匹配/新全景，默认关闭或灰度。
5. **明确不补**：工时、甘特、Wiki、思维导图、移动端、复杂项目集、完整多角色签核、分布式压测资源池。

## 1. 现状断点诊断

### 1.1 理想链路

```text
反馈/需求 → 迭代 → 任务/文档/原型
       → 代码提交 / MR
       → 接口/依赖/DDL 快照
       → 测试用例 / 场景 / 计划 / 执行 / 报告
       → 缺陷（引入 / 修复）
       → 质量门禁
       → Release / Deploy
```

### 1.2 断点清单

| 编号 | 断点 | 现状 | 影响 |
| --- | --- | --- | --- |
| B1 | 需求↔代码弱关联 | commit message 正则抽键，主要挂 `iteration` | 需求看不全代码，看板统计不准 |
| B2 | 无统一 Artifact Link | 关联散落多表/文本字段/`e2e_trace` | 难统一查询、可视化、审计 |
| B3 | e2e 未成主路径 | API 有、产品面弱 | 全链路像拼接口 |
| B4 | 测试推荐粗 | `related_files/apis` + `ILIKE` | 噪音大、QA 不信 |
| B5 | 执行↔版本/环境弱 | 计划/环境/版本维度不统一 | 「这版测过什么」难答 |
| B6 | 缺陷引入自动化弱 | 有 `INTRODUCE/FIX` 类型，推断不足 | 根因依赖人工 |
| B7 | Release 聚合弱 | 缺 ChangeSet / 驾驶舱 | 发版决策分散 |
| B8 | 迭代层薄 | Iteration 存在但未闭环 | 「本迭代交付了什么」难讲 |
| B9 | 部署节点弱 | 协议有 `DEPLOY_RECORD`，产品面弱 | 线上对照不清 |
| B10 | 角色入口散 | 工作台/权限雏形 | 有数据找不到入口 |

### 2.1 工件类型（Artifact Type）

| type | 说明 | 现有主键来源 |
| --- | --- | --- |

| `TEST_EXECUTION` | 执行 | `test_execution.id` |
| `TEST_REPORT` | 报告 | `test_report.id` |

| `DEPLOY` | 部署记录 | 新表或事件派生 |
| `FEEDBACK` | 反馈 | 反馈表 id |

### 2.2 边类型（link_type）

| link_type | 含义 | 典型 from → to |
| --- | --- | --- |
| `IMPLEMENTS` | 代码实现需求 | `CHANGE_EVENT` → `REQUIREMENT` |
| `BELONGS_TO` | 归属迭代 | `REQUIREMENT`/`CHANGE_EVENT` → `ITERATION` |
| `COVERS` | 用例覆盖 | `TEST_CASE` → `REQUIREMENT`/`API`/`FILE` |
| `TESTS` | 执行验证 | `TEST_EXECUTION` → `CHANGE_EVENT`/`RELEASE` |
| `INTRODUCES` | 提交引入缺陷 | `CHANGE_EVENT` → `BUG` |
| `FIXES` | 提交修复缺陷 | `CHANGE_EVENT` → `BUG` |
| `BLOCKS` | 缺陷阻塞发布 | `BUG` → `RELEASE` |
| `GATES` | 门禁约束版本 | `QUALITY_GATE` → `RELEASE` |
| `SHIPPED_IN` | 纳入版本 | `REQUIREMENT`/`CHANGE_EVENT` → `RELEASE` |
| `DEPLOYED_AS` | 版本对应部署 | `RELEASE` → `DEPLOY` |
| `DERIVED_FROM` | 反馈派生 | `REQUIREMENT`/`BUG` → `FEEDBACK` |

| 方法 | 路径 | 说明 |

## 8. Phase A 详细规格（接口 / 表结构 / 前端）

> Phase A 目标：接通 **需求↔代码**，建立 **统一边表**，交付 **关联治理 + 需求全景 + 版本全景 + 完整度**。  
> 预计 Flyway：`V18__trace_core.sql`（若仓库已有更高版本号，顺延）；P0 修订项（`change_event.message` 列、REQ 规则正则修正）以 **`V19`** 追加，见 §8.2.8 与 §8.2.2。  
> 特性开关：`evotrace.trace.v2.enabled=true` 时启用自动建边与新 UI 入口。

### 8.1 范围与非范围

**范围内**

1. `requirement.req_key` 与生成/唯一约束  
2. 项目级关联规则配置  
3. `artifact_link` 表 + 写入服务 + 双写  
4. CommitHandler / MR 路径解析建 `IMPLEMENTS` / `BELONGS_TO`  
5. 关联治理中心 API + 页面  
6. 需求全景 API + 页面增强  
7. 版本全景（Release Cockpit）基础版  
8. 链路完整度计算  
9. 审计：补链/断链/确认/忽略  

**范围外（留给 B+）**

- 推荐引擎 v2、`test_case_coverage`  
- 缺陷 INTRODUCES 自动推断、门禁豁免  
- 变更/缺陷独立全景页完善、部署表、迭代复盘  
- 完整 `trace/path` 图算法（A 可用邻接汇总代替）

### 8.2 数据模型（表结构）

#### 8.2.1 改表：`requirement`

```sql
ALTER TABLE requirement
    ADD COLUMN IF NOT EXISTS req_key VARCHAR(64);

-- 项目内唯一；允许历史数据先回填再加约束
CREATE UNIQUE INDEX IF NOT EXISTS uk_requirement_project_req_key
    ON requirement (project_id, req_key)
    WHERE req_key IS NOT NULL;

CREATE INDEX IF NOT EXISTS idx_requirement_req_key
    ON requirement (project_id, lower(req_key));
```

**回填策略（迁移或启动任务）**

1. 若 `external_key` 匹配 `^[A-Za-z]+[-_]?\d+$`，则 `req_key = upper(规范化)`  
2. 否则按项目前缀生成：`{prefix}-{id}`，默认前缀 `REQ`  
3. 控制台创建需求时：未传则自动生成；传入则校验唯一

#### 8.2.2 新表：`project_link_rule`

项目级关联规则（协作约定的可执行部分）。

```sql
CREATE TABLE project_link_rule (
    id              BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    project_id      BIGINT NOT NULL REFERENCES project(id),
    name            VARCHAR(128) NOT NULL,
    enabled         BOOLEAN NOT NULL DEFAULT TRUE,
    priority        INT NOT NULL DEFAULT 100,          -- 越小越先匹配
    pattern         VARCHAR(512) NOT NULL,             -- Java/正则，含命名组 reqKey
    extract_group   VARCHAR(64) NOT NULL DEFAULT 'reqKey',
    apply_to        VARCHAR(64) NOT NULL DEFAULT 'COMMIT_MESSAGE',
        -- COMMIT_MESSAGE | MR_TITLE | MR_BODY | BRANCH_NAME
    link_type       VARCHAR(32) NOT NULL DEFAULT 'IMPLEMENTS',
    confidence      INT NOT NULL DEFAULT 90,           -- 0-100
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at      TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX idx_link_rule_project ON project_link_rule (project_id, enabled, priority);
```

**默认种子规则（每项目可复制全局模板）**

| name | pattern | apply_to | confidence |
| --- | --- | --- | --- |
| REQ key | `(?i)\b(?<reqKey>REQ[-_]?\d+)\b` | COMMIT_MESSAGE, MR_TITLE, BRANCH_NAME | 95 |
| JIRA key | `(?i)\b(?<reqKey>[A-Z][A-Z0-9]+-\d+)\b` | COMMIT_MESSAGE, MR_TITLE | 90 |
| Hash issue | `#(?<reqKey>\d{3,})\b` | COMMIT_MESSAGE | 70（仅当项目开启 hash 映射） |

> **P0-2 修订**：REQ key 正则由 `\d{3,}` 放宽为 `\d+`，与自动生成键 `REQ-{id}`（小 id 时位数可能 < 3）保持一致，避免小 id 需求无法自动关联。V18 已落库的种子仍为 `\d{3,}`，需在 V19 中 `UPDATE project_link_rule SET pattern='(?i)\\b(?<reqKey>REQ[-_]?\\d+)\\b' WHERE name='REQ key'`。

#### 8.2.3 新表：`project_trace_setting`

协作约定与开关。

```sql
CREATE TABLE project_trace_setting (
    project_id           BIGINT PRIMARY KEY REFERENCES project(id),
    req_key_prefix       VARCHAR(32) NOT NULL DEFAULT 'REQ',
    auto_link_enabled    BOOLEAN NOT NULL DEFAULT TRUE,
    hash_issue_enabled   BOOLEAN NOT NULL DEFAULT FALSE,  -- #123 → 需求 id/external
    branch_template      VARCHAR(256) DEFAULT 'feature/{reqKey}-*',
    commit_template      VARCHAR(256) DEFAULT '{reqKey} <summary>',
    ai_suggest_enabled   BOOLEAN NOT NULL DEFAULT FALSE,  -- A 期可只留开关，实现可 stub
    updated_at           TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

#### 8.2.4 新表：`artifact_link`（核心）

```sql
CREATE TABLE artifact_link (
    id              BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    project_id      BIGINT NOT NULL REFERENCES project(id),
    from_type       VARCHAR(32) NOT NULL,
    from_id         VARCHAR(128) NOT NULL,          -- 统一字符串，数值 id 转字符串
    to_type         VARCHAR(32) NOT NULL,
    to_id           VARCHAR(128) NOT NULL,
    link_type       VARCHAR(32) NOT NULL,
    confidence      INT NOT NULL DEFAULT 100,
    source          VARCHAR(32) NOT NULL,
        -- AUTO_COMMIT_KEY | AUTO_MR | AUTO_BRANCH | AUTO_AI | MANUAL | IMPORT | MIGRATION
    status          VARCHAR(16) NOT NULL DEFAULT 'ACTIVE',
        -- ACTIVE | PENDING | REJECTED | IGNORED
    created_by      VARCHAR(64),
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    meta            JSONB NOT NULL DEFAULT '{}'::jsonb
        -- 例: {"matchedText":"REQ-1001","applyTo":"COMMIT_MESSAGE","eventId":"..."}
);

-- 活跃边防重复
CREATE UNIQUE INDEX uk_artifact_link_active
    ON artifact_link (project_id, from_type, from_id, to_type, to_id, link_type)
    WHERE status = 'ACTIVE';

CREATE INDEX idx_artifact_link_from
    ON artifact_link (project_id, from_type, from_id, link_type);

CREATE INDEX idx_artifact_link_to
    ON artifact_link (project_id, to_type, to_id, link_type);

CREATE INDEX idx_artifact_link_pending
    ON artifact_link (project_id, status, confidence)
    WHERE status IN ('PENDING', 'ACTIVE');
```

**Phase A 必写边**

| 场景 | from | to | link_type | source |
| --- | --- | --- | --- | --- |
| commit 命中 req_key | `CHANGE_EVENT` / event_id | `REQUIREMENT` / id | `IMPLEMENTS` | `AUTO_COMMIT_KEY` |
| MR 标题命中 | 同上 | 同上 | `IMPLEMENTS` | `AUTO_MR` |
| 分支名命中 | 同上 | 同上 | `IMPLEMENTS` | `AUTO_BRANCH` |
| 需求归属迭代 | `REQUIREMENT` | `ITERATION` | `BELONGS_TO` | `MANUAL`/`MIGRATION` |
| 变更归属迭代（兼容旧逻辑） | `CHANGE_EVENT` | `ITERATION` | `BELONGS_TO` | `AUTO_COMMIT_KEY` |
| 人工补链 | `CHANGE_EVENT` | `REQUIREMENT` | `IMPLEMENTS` | `MANUAL` |
| 版本纳入（自动时间窗/tag 差） | `CHANGE_EVENT`/`REQUIREMENT` | `RELEASE` | `SHIPPED_IN` | `MIGRATION`/`AUTO_*` |

**置信度与状态策略（A）**

| confidence | 默认 status | 治理动作 |
| --- | --- | --- |
| ≥ 85 | `ACTIVE` | 直接生效，可在治理中心断开 |
| 60–84 | `PENDING` | 待确认 |
| < 60 | 不写边或 `PENDING`（配置） | 仅进入建议列表 |

#### 8.2.8 补充：`change_event.message` 持久化（V19，P0-1）

> 现状：`change_event` 表无 message 列，commit 消息仅在摄入时从 payload 读取用于解析 `iteration`，未落库。这会导致治理「未关联提交」/「悬空键」列表无法返回 `message`，且 §8.6.1 基于 commit message 的悬空键即时检测无数据来源。

```sql
-- V19：为分区表父表加列，自动透传到各 RANGE 分区
ALTER TABLE change_event
    ADD COLUMN IF NOT EXISTS message VARCHAR(2048);
```

- 摄入侧（`CommitHandler` / `MrMergedHandler`）在建事件时写入 `payload.message()`。
- `ChangeEvent` 实体与写入 SQL 同步增加 `message` 字段。
- `LinkRuleEngine` 摄入期建边时，将 `matchedText` 写入 `artifact_link.meta`（见 §8.2.4），供「待确认边」展示命中文本。
- 治理查询（`unlinked-changes` / `dangling-keys`）直接读取 `change_event.message`。

**完整度算法（A 固定权重，可配置留到 B）**

```text
score = Σ weight(check) for passed
HAS_CODE:            存在 IMPLEMENTS 边（CHANGE→本需求）     25
HAS_TEST_CASE:       test_case.requirement_id = 本需求       20
HAS_EXECUTION:       上述用例 14 日内有 execution             15
NO_BLOCKING_BUG:     无 severity∈(P0,P1) 且 status 未关闭    25
SHIPPED_OR_TARGET:   有 SHIPPED_IN 或 target_version 非空    10
GATE_PASS_IF_RELEASED: 若已 SHIPPED_IN 则最新门禁 PASSED，否则计通过  5
```

**ChangeSet 自动纳入规则（A 基础）**

- 筛选：作者、时间范围、分支

### 8.6 后端处理时序（A）

#### 8.6.1 提交入库建边

```text
Webhook/SDK → Ingestion → CommitHandler.persist
  → 旧逻辑: iteration_id
  → LinkRuleEngine.onCommit(event, message, branch)
       → match keys
       → find requirement by req_key
       → upsert artifact_link IMPLEMENTS (ACTIVE/PENDING)
       → if key not found: record dangling (redis/表/治理查询时即时检测均可)
  → AI summary (unchanged)
```

**悬空键检测（推荐）**：基于持久化的 `change_event.message`，对规则命中但 `requirement.req_key` 不存在的键，`LEFT JOIN requirement` 即时检测（见 §8.2.8 的 message 落库）；若需审计创建动作再落审计表。

#### 8.6.2 版本 ChangeSet rebuild

```text
POST rebuild-changeset(version)
  → resolve release + previous release
  → select change_events in window
  → for each: SHIPPED_IN RELEASE
  → for each IMPLEMENTS req: SHIPPED_IN RELEASE (requirement)
  → optional: refresh e2e_trace for release
```

## 9. 全局验收剧本（全期）

1. 建需求 `REQ-1001` → 两次规范提交 → 需求全景 2 条 IMPLEMENTS。  
2. 无键提交进未关联池 → 人工挂上 → audit 可查。  
3. 版本对比/推荐（B）→ 带 reason 生成计划 → 绑定环境执行。  
4. 失败用例一键建缺陷（B）→ 修复 commit 自动 FIXES。  
5. 门禁失败 → Cockpit 红灯 → 豁免并审计（B）。  
6. Release ChangeSet → 全景展示需求/测试/缺陷/门禁。  
7. 部署 prod → 反查版本与需求（C）。  
8. 矩阵报表下钻覆盖率与逃逸（C）。

## 11. 结论

完整度瓶颈在 **关联可靠性、全景产品化、治理闭环**，不在继续堆叠协作套件。

落地顺序固定为：

1. **Phase A：Trace Core（边表 + 规则 + 治理 + 需求/版本全景）**  
2. **Phase B：拧紧测试与缺陷边，门禁进驾驶舱**  
3. **Phase C：迭代/部署/度量运营化**  
4. **Phase D：AI 与 onboarding 增强**

本文 §8 可作为 Phase A 直接拆分开发任务与联调契约的唯一细则；Phase B+ 实施前应另开小节补接口字段级规格（或在本文追加修订记录）。
