## 1. 架构总览

### 1.1 设计原则

1. **事件驱动**：一切变更统一抽象为不可变事件，摄入与处理解耦
2. **全链路可达**：需求 → 代码 → 测试 → 缺陷 → 发布，任意节点可双向追溯
3. **角色视图分离**：PM / Dev / QA / Ops 各自看到自己关心的视图，底层数据互联
4. **接入协议统一**：任何语言只面向 Envelope 协议
5. **AI 可插拔与可降级**：模型提供方通过配置切换，AI 故障不影响采集主链路
6. **私有化优先**：全栈 docker-compose 一键拉起

## 3. 核心设计

### 3.1 事件摄入管道

```
接入方 → HMAC签名校验 → 幂等检查(DB唯一约束)
       → Kafka(evo.events.raw, partitionKey=projectKey)
       → ChangeEventConsumer(策略路由)
         → CommitHandler: 持久化change_event + change_file + 需求关联
         → InventoryReportHandler: upsert应用记录
       → AiSummaryWorker(evo.tasks.ai): PromptLoader + ChatClient → SemanticUnit
       → SubscriptionMatcher: 匹配订阅规则 → 多渠道通知
```

### 3.2 破坏性变更检测

```
版本对比 → BreakingChangeDetector:
  Level 1 (CRITICAL): API_DELETED / DDL_DROP_COLUMN → 15分/个
  Level 2 (WARNING):  FIELD_NARROWED / 依赖大版本升级 → 5分/个
  Level 3 (INFO):     API_MODIFIED / CONFIG_KEY_REMOVED
→ 持久化 breaking_change_alert → 订阅通知 → 质量门禁扣分
```

### 3.3 影响面分析引擎

```
变更API列表 → BFS遍历 api_dependency_graph(最大深度5)
  → affectedServices + directCallers + suggestedRegression
  → 发布风险评分(impactRadius维度)
  → 测试推荐(匹配related_apis测试用例)
```

### 3.4 发布风险评分算法

```
Score = Volume(0-30) + Breaking(0-25) + BugHistory(0-20) + Impact(0-15) + Time(0-10)

Volume:     commits≤5→5, ≤20→15, ≤50→22, >50→30
Breaking:   每个CRITICAL→15pt, 每个WARNING→5pt (max 25)
BugHistory: 0→0, ≤3→8, ≤10→14, >10→20
Impact:     affected≤2→3, ≤10→8, >10→15
Time:       周五16点后/周末→10, 深夜→6, 正常→2
```

### 3.5 测试推荐引擎

```
变更文件列表 → (1) 按文件名匹配test_case.related_files
             → (2) 按接口匹配test_case.related_apis
             → 去重 → 按P0/P1/回归分类
             → 生成回归范围建议 + 风险等级
```

### 3.6 质量门禁五维检查

```
Check 1 (30pt): 未关闭P0/P1缺陷数 = 0?
Check 2 (25pt): 失败测试用例数 = 0?
Check 3 (20pt): 未确认破坏性变更 = 0?
Check 4 (15pt): 变更文件测试覆盖率 ≥ 60%?
Check 5 (10pt): 发布风险评分 ≤ 60?
→ 5项全部通过 → PASSED → 可以发布
→ 任意未通过 → FAILED → 显示不通过项
```

### 3.7 端到端全链路追踪

```
任意节点 → E2ETrace:
  需求(R)→迭代(R)→代码变更(C)→测试用例(C)→缺陷(C)→版本(C)
  
  版本视角: 版本号 → 关联的所有需求/变更/缺陷/测试/质量门禁
  Bug视角:   Bug → Fix Commit → Changed Files → Related Tests
```

### 3.8 AI 分析架构

```
AiSummaryWorker (Kafka evo.tasks.ai)
├── PromptLoader     → templates from evotrace-ai-prompts classpath
├── ModelRouter      → ChatClient (OpenAI兼容协议)
├── StructuredOutput → BeanOutputConverter → ChangeSummaryResult
├── TokenMeter       → ai_usage 表记录
└── FeedbackLoop     → 人工修订 → Few-shot样本回流
```

## 6. 安全设计

- **认证**：控制台 JWT（12h TTL）；接入方 API Key + HMAC-SHA256
- **授权**：RBAC 两级（工作空间角色 × 项目角色）
- **数据安全**：敏感值 SD K端强制脱敏 + 服务端二次校验；apiSecret 只存 hash
- **审计**：audit_log 表记录所有敏感操作

## 7. 可靠性与性能

| 场景 | 设计 |
| --- | --- |
| 摄入突发 | Kafka 削峰 + 令牌桶限流 + 虚拟线程水平扩展 |
| 消费失败 | 重试 → DLT → 控制台重放 |
| AI 不可用 | 任务滞留 Kafka；摘要状态 PENDING 恢复后追平 |
| 存储膨胀 | 按月分区 + 保留策略 + 清单项内容寻址去重 |

## 8. 可观测性

- **指标**：ingest_events_total / ai_tokens_total / snapshot_build_duration / dlt_events_total
- **链路**：OpenTelemetry traceId 从 Gateway → Kafka header → 消费者 → AI 调用
- **日志**：JSON 结构化；AI 请求/响应脱敏后留存
