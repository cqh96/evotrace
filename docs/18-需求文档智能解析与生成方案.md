## 1. 背景与目标

### 1.1 背景

PM 日常拿到的是各种形态的需求材料：原型分享链接（如 `https://codesign.qq.com/app/s/xxx`）、PDF/Word/Markdown 版 PRD、高保真原型 + 轻量 PRD 的组合。目前平台的需求（`requirement`）只能手工录入或 AI 扩写单条，从原始材料到"需求看板 + 测试用例"全靠人肉拆解，成本高、易遗漏。

### 1.2 目标

| 维度 | 目标 |
| --- | --- |
| 输入 | 支持三类材料：① 外部链接（原型/PRD 页面）② 文档上传（pdf/docx/md/txt/html）③ 原型链接 + 轻量 PRD 组合输入 |
| 产出 | AI 解析生成**结构化需求列表**（标题/用户故事/验收标准/优先级/业务价值）+ 每条需求的**测试用例建议** |
| 落库 | 解析结果先预览编辑，确认后批量写入需求看板（`requirement`）并关联生成测试用例（`test_case.requirement_id`） |
| 降级 | 无可用模型时返回确定性骨架或明确提示，绝不报错阻断（沿用 `PmAiGateway` 门控） |
| 可追溯 | 原始材料留档（blob + 来源链接），需求可回溯到出处文档 |

## 2. 现状与差距分析

| 现状 | 差距 |
| --- | --- |
| 需求看板/状态机/文档版本链/原型/任务拆分已完整（`RequirementService`、`RequirementWorkbenchController`） | 需求只能靠手工录入或单条 AI 扩写（`ai-expand`），无批量解析入口 |
| AI 用例生成已有（`AiTestCaseGenerator`），但必须绑定变更事件、逐条人工保存 | 不支持"从需求文本直接生成用例"并批量落库 |
| `requirement.prototype_url` 字段已存在 | 仅存字符串，无任何抓取/解析逻辑 |
| 上传链路有完整样例（`importCases`：MultipartFile + poi-ooxml 解析 Excel） | 无 pdf/docx/html 解析能力（缺 tika/pdfbox/jsoup 依赖） |
| 外部 HTTP 调用有成熟范本（`GitLabDiffFetcher`：HttpClient + 超时 + 截断 + 降级） | 无"抓取外部页面正文"能力；codesign 等 SPA 页面静态抓取可能拿不到内容 |
| 大文本处理有规约（`max-diff-chars=12000` 截断 + blob 外置） | 需求文档尚无原文留档表 |

## 3. 方案设计

### 3.1 总体流程

```
┌─────────────── 输入层 ───────────────┐
│ ① 链接  ② 文档上传  ③ 原型链接+轻PRD │
└───────┬──────────────────────────────┘
        ▼
MaterialIngestService          ← 新增（server/.../requirement/）
  ├─ 链接：JDK HttpClient 抓取（30s 超时/200KB 截断/失败降级提示）→ HTML 正文提取
  ├─ 文件：Apache Tika 解析（pdf/docx/html/txt/md/xlsx）
  └─ 组合：链接正文 + PRD 文本拼接，标注来源段落
        ▼
原文留档：BlobStoreService.put() → requirement_source_doc（V23）
        ▼
PmAiGateway + 新模板 requirement-doc-parse.st
  → 严格 JSON：requirements[] {title, user_story, acceptance_criteria,
     priority, business_value, suggested_cases[] {title, steps[], test_type, priority}}
        ▼
┌──────── 预览确认（前端 Drawer/Dialog）────────┐
│ 需求卡片列表可编辑/删除/调优先级；用例可勾选   │
└───────┬──────────────────────────────────────┘
        ▼ 确认提交
批量落库：RequirementService.upsert（source=AI_DOC）+ TestCaseService.create（关联 requirement_id，标记 ai_generated）
```

**同步 vs 异步**：P0 同步处理（解析文本 ≤ 20 万字符，模型超时 120s 内可完成）；超大文档或批量链接在 P1 接入 `evo.tasks.ai` 异步模式（新增 taskType=`DOC_PARSE`，复用 AiSummaryWorker 骨架 + DLT）。

### 3.2 数据库迁移（V23__requirement_ai_parse.sql）

```sql
CREATE TABLE requirement_source_doc (
    id           BIGSERIAL PRIMARY KEY,
    project_id   BIGINT NOT NULL REFERENCES project(id),
    source_type  VARCHAR(20) NOT NULL,        -- LINK / FILE / PROTOTYPE_PRD
    file_name    VARCHAR(512),
    external_url VARCHAR(1024),
    blob_ref     VARCHAR(128),                -- 原文 blob（BlobStoreService）
    char_count   INT,
    parse_status VARCHAR(20) NOT NULL DEFAULT 'PENDING',  -- PENDING/PARSED/FAILED
    model        VARCHAR(128),
    parse_result JSONB,                       -- AI 原始结构化输出（留档复查）
    created_by   VARCHAR(64),
    created_at   TIMESTAMPTZ NOT NULL DEFAULT now()
);

ALTER TABLE requirement ADD COLUMN IF NOT EXISTS source_doc_id BIGINT REFERENCES requirement_source_doc(id);
ALTER TABLE test_case   ADD COLUMN IF NOT EXISTS ai_generated BOOLEAN NOT NULL DEFAULT false;
-- requirement.source 枚举语义扩展：新增 AI_DOC（VARCHAR 无约束，仅约定）
```

### 3.3 后端改动

#### 3.3.1 新增依赖（evotrace-server/pom.xml）

```xml
<dependency>
    <groupId>org.apache.tika</groupId>
    <artifactId>tika-parsers-standard-package</artifactId>
    <version>2.9.2</version>
</dependency>
```

Tika 单库覆盖 pdf/docx/html/txt/md/xlsx，避免同时引入 pdfbox+jsoup+poi 多依赖。HTML 正文提取走 Tika 的 `BodyContentHandler`，不再单引 jsoup。

#### 3.3.2 新增类（均放 `io.evotrace.server.requirement` 包）

| 类 | 职责 |
| --- | --- |
| `MaterialIngestService` | 三类输入统一解析为纯文本：链接抓取（仿 `GitLabDiffFetcher`：HttpClient、30s 超时、200KB 截断、失败返回错误提示不抛异常）；文件走 Tika；组合输入拼接并标注来源 |
| `RequirementDocParser` | 调 `PmAiGateway.generate` + `requirement-doc-parse` 模板 → 结构化 `ParsedRequirementDoc` record；文本超 20 万字符按章节截断（优先保留标题层级）；无模型时返回 null |
| `RequirementImportService` | 预览确认后批量落库：循环 `RequirementService.upsert`（source=`AI_DOC`，回填 `source_doc_id`），再按勾选批量 `TestCaseService.create`（`requirement_id` 关联 + `ai_generated=true`）；整体单事务 |
| `RequirementImportController` | 见 3.3.3 接口，鉴权/取数/异常处理完全照抄 `RequirementWorkbenchController` 惯例 |

复用而不改动：`ModelRouter`、`PromptLoader`、`BlobStoreService`（原文外置，`evotrace.blob.dir`）、`GlobalExceptionHandler`。

#### 3.3.3 API 设计（挂 `/api/v1/pm`，JWT 登录态）

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/requirements/parse-link` | body：`{projectKey, url, prdText?}`；prdText 非空即"原型+轻PRD"组合模式；返回 parseId + 结构化预览 |
| POST | `/requirements/parse-doc` | multipart：`projectKey` + `file`（≤20MB）；返回 parseId + 结构化预览 |
| GET | `/requirements/parse-result/{parseId}` | 复查解析留档 |
| POST | `/requirements/import-confirm` | body：编辑后的需求+勾选用例 JSON；批量落库，返回创建的需求/用例 ID 清单 |

### 3.4 Prompt 模板（evotrace-ai-prompts 新增）

`prompts/requirement-doc-parse.st`，沿用"严格 JSON + 中文"约定，关键约束：

- 输出 schema：`{requirements:[{title,user_story,acceptance_criteria,priority(P0-P3),business_value,suggested_cases:[{title,test_type(FUNCTIONAL/REGRESSION/API),priority,steps:[{step,expected}]}]}]}`
- 每条需求 3-6 条验收标准；每条需求 2-5 条用例建议，含 1 条异常/边界场景
- 原型类材料（元素清单+页面结构）侧重交互用例；PRD 类材料侧重业务规则
- 材料信息不足时宁缺毋滥，字段留空不编造

### 3.5 前端改动（evotrace-ui）

| 位置 | 改动 |
| --- | --- |
| `PMDashboardView.vue` 工具栏 | 新增「智能导入」按钮，弹出 `RequirementImportDialog.vue`（新组件，放 `components/pm/`） |
| 导入 Dialog | 三个 Tab：链接 / 文档上传（复刻 `caseFileApi.import` 的 FormData+进度模式）/ 原型+轻PRD（链接输入框 + 文本域）；提交后进入预览态 |
| 预览态 | 需求卡片列表（标题/优先级可编辑，验收标准/user_story 折叠展示，可删除条目）；每条需求下用例勾选列表；底部「确认导入」→ 调 import-confirm → 看板刷新 |
| `api/pm.ts` | 新增 `parseLink / parseDoc / getParseResult / importConfirm` 四个封装 |
| 需求详情 Drawer | source=`AI_DOC` 的需求展示来源链接/文件名 + 解析时间，可跳转 parse-result 复查 |

### 3.6 链接抓取的务实边界

codesign.qq.com 等 SPA 原型站静态抓取大概率只能拿到壳 HTML。策略：

1. 抓取后正文 < 500 字符时判定"动态渲染无法解析"，明确提示用户改用「导出 PNG/PDF 上传」或「粘贴 PRD 文本」；
2. 组合模式（③）天然规避此问题：链接仅作 `prototype_url` 留档，解析以 PRD 文本为主；
3. P2 再评估 Headless 渲染（Playwright/Selenium 已有依赖可用于服务端渲染抓取），本期不做。

## 5. 风险与依赖

| 风险 | 应对 |
| --- | --- |
| SPA 链接抓不到正文 | 明确降级提示 + 组合输入规避 + P2 渲染抓取 |
| AI 输出 JSON 不稳定 | PmAiGateway 门控（失败返回 null）+ 前端预览态兜底人工编辑 |
| 大文档超时/超 token | 20 万字符截断 + 章节优先保留 + P1 异步化 |
| Tika 依赖体积大（~60MB） | 仅 server 模块引入；镜像构建体积可接受，后续可换 tika-core+单 parser 裁剪 |
| 批量落库部分失败 | import-confirm 单事务，失败整体回滚并返回明细 |

---

## 6. 验收标准

1. 上传一份 PRD（docx/pdf/md），60s 内返回结构化预览，需求 ≥ 3 条且字段完整；
2. 确认导入后看板出现对应需求（source=AI_DOC，可追溯原文档），勾选用例入库且 `requirement_id` 关联正确、`ai_generated=true`；
3. 链接抓取失败时给出可操作的降级提示，不产生 5xx；
4. 无可用模型时接口返回明确降级文案，不阻断看板其他功能；
5. 组合模式：粘贴轻 PRD + 原型链接，解析以 PRD 为准且需求回写 `prototype_url`。
