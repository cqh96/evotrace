## 1. 背景与目标

### 1.1 背景

1. **检索现状是 PostgreSQL ILIKE**：演化问答（`QaController`）靠中文 2-gram 切词 + `ai_semantic_unit.content ILIKE` 命中，整句匹配几乎无效；测试用例列表（`TestCaseService`）、风险/热点分析（`RiskScorer`/`HotspotAnalyzer`）同样是 ILIKE 统计。
2. **ES 是架构预留组件**：架构设计将 Elasticsearch 定位为全文检索引擎，docker-compose 已编排 ES 8.14.3（端口 9200），但 server 无任何 ES 依赖与代码。
3. **pgvector 同样未启用**：`ai_embedding` 表（1024 维）与 `spring-ai-starter-vector-store-pgvector` 依赖已就位，代码零调用。语义检索走 pgvector 还是 ES 需在本方案中明确分工。
4. **数据规模增长**：V2.5 已将事件/分析分流至 ClickHouse，业务文本（需求/用例/缺陷/commit/摘要）仍压在 PG 上，ILIKE 全表扫描随数据量线性恶化。

### 1.2 目标

| 维度 | 目标 |
| --- | --- |
| 检索质量 | 中文分词（IK）全文检索替代 ILIKE，问答引用命中率显著提升 |
| 检索范围 | 统一搜索入口覆盖需求/用例/缺陷/commit/AI 摘要五类文本 |
| 性能 | 万级文档检索 P95 < 100ms，卸下 PG 的 ILIKE 全表扫描压力 |
| 接入姿态 | 复刻 ClickHouse 模式：Kafka sink 双写 + 开关灰度 + 未启用优雅降级 |
| 边界清晰 | ES 管全文检索，pgvector 管语义向量，互不越界 |

## 2. 现状与差距分析

| 现状 | 差距 |
| --- | --- |
| 问答检索：`ai_semantic_unit.content ILIKE '%kw%'`（2-gram 切词），`occurred_at DESC LIMIT 5` | 无分词、无相关度排序、无高亮，长尾问题命中率低 |
| 用例/缺陷检索：`title ILIKE ? OR tags ILIKE ?` | 无字段权重，描述/steps 等长文本不参与检索 |
| commit 检索：`change_event.commit_message` 无搜索入口 | 演化追踪无法按 commit 内容回溯 |
| ES 容器已起（8.14.3 single-node，关闭 xpack 安全） | server 无依赖、无索引、无数据同步链路 |
| `ai_embedding` + pgvector 依赖已备 | 无语义检索代码；需明确与 ES 的分工 |

> 范围说明：本期只做**全文检索**（keyword + 分词），语义/向量检索（pgvector RAG 升级）不在本方案内，仅在第 6 章说明边界与后续衔接。

## 3. 方案设计

### 3.1 总体架构

```
PostgreSQL (业务事务)
   │  增量：CDC 式应用内双写        存量：BackfillJob 批量回填
   ▼
Kafka evo.events.raw ──► EsEventSink (新 consumer group)
   │                            │ 需求/用例/缺陷：业务 Service 内同步双写（同事务提交后发 Kafka 轻量通知或直接 REST bulk）
   ▼                            ▼
                    Elasticsearch 8.14.3
                    ┌──────────────────────┐
                    │ evo-semantic-unit    │ AI 摘要（问答语料）
                    │ evo-change-event     │ commit message
                    │ evo-requirement      │ 需求
                    │ evo-test-case        │ 测试用例
                    │ evo-bug-ticket       │ 缺陷
                    └──────────────────────┘
                              ▲
                              │ EsSearchService（统一检索门面，未启用时降级走 PG ILIKE）
                              ▼
        QaController / TestCaseService / 全局搜索 API
```

**写入链路选型**：事件类（commit/摘要）复用既有 Kafka 管道新增 `EsEventSink`；业务类（需求/用例/缺陷）数据量小、实时性要求高，在对应 Service 保存后同步调 ES index（失败仅记 warn，由对账任务兜底），不引入 CDC 中间件。

### 3.2 依赖与配置

#### 3.2.1 依赖

`evotrace-server/pom.xml` 新增（Spring Boot 4 已管理版本，无需显式指定）：

```xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-data-elasticsearch</artifactId>
</dependency>
```

#### 3.2.2 配置（仿 `evotrace.clickhouse` 结构）

`application.yml` 新增：

```yaml
evotrace:
  elasticsearch:
    enabled: ${ES_ENABLED:false}
    uris: ${ES_URIS:http://localhost:9200}
    username: ${ES_USERNAME:}
    password: ${ES_PASSWORD:}
    dual-write: ${ES_DUAL_WRITE:true}      # 写入侧灰度开关
    backfill:
      batch-size: 500
```

未启用时所有 ES Bean 以 `ObjectProvider` 方式注入并降级，与 `ClickhouseEventSink` 模式一致。

### 3.3 索引设计

统一索引前缀 `evo-`，每类文档一个索引；中文文本字段用 IK 分词器（需在 ES 镜像中预装 `analysis-ik`，部署手册同步更新）。

#### 3.3.1 `evo-semantic-unit`（AI 摘要，问答核心语料）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | keyword | PG 主键 |
| project_id | keyword | 租户隔离过滤条件 |
| target_type / target_id | keyword | CHANGE_EVENT/RELEASE/ITERATION |
| kind | keyword | SUMMARY/RELEASE_NOTE/QA |
| content | text (ik_max_word) + .keyword | 摘要正文，检索主字段 |
| occurred_at | date | 排序（取关联 change_event.occurred_at） |

settings：`number_of_shards: 1`、`number_of_replicas: 0`（单机起步，生产可调）。

#### 3.3.2 `evo-change-event`（commit 检索）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| event_id / project_id / app_id | keyword | |
| event_type / branch / author | keyword | 过滤维度 |
| commit_sha | keyword | |
| commit_message | text (ik_max_word) | 检索主字段 |
| occurred_at | date | 排序 |

#### 3.3.3 `evo-requirement` / `evo-test-case` / `evo-bug-ticket`

三个索引结构同构，均为：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id / project_id | keyword | |
| title | text (ik_max_word)，boost 3 | 标题权重最高 |
| description / user_story / steps 等 | text (ik_max_word) | 正文 |
| tags / status / req_key | keyword | 过滤与精确跳转 |
| updated_at | date | 排序 |

> 文档均带 `project_id`，所有查询强制 `term` 过滤，天然租户隔离；不建跨项目聚合索引。

### 3.4 写入链路

#### 3.4.1 事件类：EsEventSink（新增 Kafka consumer）

- 新建 `server/.../search/EsEventSink.java`，完全复刻 `ClickhouseEventSink` 写法：
  - `@KafkaListener(topics = "evo.events.raw", groupId = "evo-es-sink")`
  - `@Value("${evotrace.elasticsearch.enabled:false}")` + `ObjectProvider<ElasticsearchClient>` 优雅降级
  - 消费 Envelope → 写入 `evo-change-event`（commit_message 非空才索引）
  - try/catch 吞异常打 warn，不影响主链路；DLT 由既有 `KafkaContainerConfig` 兜底
- `AiSummaryWorker` 在 `semanticUnitRepository.save(unit)` 后同步索引到 `evo-semantic-unit`（失败记 warn，由对账兜底）。

#### 3.4.2 业务类：Service 内同步双写

- 新建 `server/.../search/EsIndexService.java`，提供 `indexRequirement/indexTestCase/indexBugTicket/deleteById` 等方法。
- 在 `RequirementService`/`TestCaseService`/缺陷 Service 的 save/delete 后调用；`dual-write=false` 时直接跳过。
- 失败仅记 warn 不阻断业务事务，由 3.4.3 对账任务兜底。

#### 3.4.3 存量回填与对账

- 新建 `EsBackfillJob`（`@Scheduled` 手动触发 + 启动时可选执行）：按 `updated_at`/`occurred_at` 分批（500/批）扫 PG → bulk 写入 ES，幂等（以 PG 主键作为 ES `_id`，重复写覆盖）。
- 每日低频对账：PG count vs ES count，差异超阈值打 warn 日志并自动重回填对应分片。

### 3.5 读取链路与降级

#### 3.5.1 统一检索门面

新建 `server/.../search/EsSearchService.java`：

```java
public interface SearchService {
    SearchResult search(String projectId, SearchScope scope, String keyword, int limit);
}
```

- `ES enabled` → 走 multi-match 查询（`title^3, content, description`）+ `project_id` term 过滤 + 高亮；
- `ES disabled` → 降级为现有 PG ILIKE 实现，**接口签名不变**，调用方无感知。

#### 3.5.2 改造点

| 调用方 | 改造内容 |
| --- | --- |
| `QaController` | ILIKE 检索段替换为 `SearchService.search(scope=SEMANTIC_UNIT)`，引用排序改用 ES `_score`；无命中回退原逻辑 |
| `TestCaseService.list(keyword)` | keyword 非空且 ES 启用时走 `evo-test-case` 检索，否则保留 ILIKE |
| 全局搜索 API（新增） | `GET /api/v1/projects/{projectKey}/search?q=&types=requirement,test_case,bug,commit,summary`，跨索引统一搜索，供前端顶部搜索框使用 |

#### 3.5.3 查询示例（问答语料）

```json
GET evo-semantic-unit/_search
{
  "query": {
    "bool": {
      "filter": [{ "term": { "project_id": "xxx" } }],
      "must": [{ "match": { "content": { "query": "支付 超时 重试", "operator": "or" } } }]
    }
  },
  "highlight": { "fields": { "content": {} } },
  "sort": [{ "_score": "desc" }, { "occurred_at": "desc" }],
  "size": 5
}
```

## 5. 风险与依赖

| 风险 | 应对 |
| --- | --- |
| IK 分词器需打进 ES 镜像 | 自定义 Dockerfile 基于 8.14.3 安装 analysis-ik，docker-compose/Helm 同步更新 |
| 双写不一致（业务成功 ES 失败） | 不阻断业务 + 每日对账 + 幂等重放；检索结果允许短暂延迟 |
| 单机 ES 可用性 | 读取侧永远保留 PG ILIKE 降级路径，ES 宕机不影响功能 |
| ES 堆内存 512MB 偏小 | 数据量增长后调 `ES_JAVA_OPTS`，部署手册给出容量建议 |
| 关闭 xpack 安全（当前 compose） | 仅内网部署；生产开启安全后通过 `evotrace.elasticsearch.username/password` 注入 |

## 6. 与 pgvector 的边界

| 能力 | 归属 | 说明 |
| --- | --- | --- |
| 关键字/全文检索、过滤、高亮、相关度排序 | **Elasticsearch** | 本方案范围 |
| 语义相似度检索（向量化问答 RAG） | **pgvector（`ai_embedding`）** | 后续 RAG 升级专项，复用 `spring-ai-starter-vector-store-pgvector` |
| 问答最终形态 | ES 召回 + pgvector 召回融合（RRF），再喂 LLM | 两路召回并存，本方案只交付 ES 一路 |

---

## 7. 验收标准

1. `ES_ENABLED=false` 时系统行为与现状完全一致（回归通过）；
2. `ES_ENABLED=true` 时问答、用例检索、全局搜索走 ES，结果含高亮，P95 < 100ms（万级文档）；
3. 存量数据回填完整（PG 与 ES 文档数对账一致）；
4. 新增 commit/摘要/需求/用例/缺陷 10 秒内可被检索到；
5. ES 宕机时自动降级 PG ILIKE，无 5xx 报错。
